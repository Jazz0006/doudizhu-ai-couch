# 23A. 通用大模型与专用训练策略

## 23A.1 总体判断

按照当前系统设计，第一版 AI 教练没有必要专门训练一个斗地主大语言模型。

现有高水平通用大模型已经足以承担大部分：

- 教学解释；
- 对话；
- 个性化表达；
- 错误总结；
- 玩家成长反馈；
- 根据玩家水平调整解释深度；

等工作。

真正需要重点研发甚至未来可能需要专门训练的，不是负责语言交流的 LLM，而是：

1. 斗地主决策模型；
2. Human Memory Model；
3. Human-Limited Decision Model；
4. Player Model；
5. Error Attribution；
6. Teaching Policy。

核心原则：

> **算法负责正确性，通用大模型负责理解、表达和教学。**

---

# 23A.2 各模块是否需要专门训练

| 模块 | 通用 LLM 是否适合 | V1 推荐方案 | 后期是否可能训练 |
|---|---|---|---|
| 最佳出牌计算 | 不适合 | 专用斗地主 AI | 是 |
| Top-K 动作评估 | 不适合 | 专用斗地主 AI | 是 |
| 精确牌局状态 | 不适合 | Game Engine | 否 |
| Human Memory | 不建议交给 LLM | 规则模型 | 是 |
| Human-Limited Decision | 通用 LLM 不可靠 | 规则/现有 AI 实验 | **很可能需要** |
| Player Rating | 不应直接由 LLM 打分 | 统计+规则 | 是 |
| Error Attribution | LLM 可辅助 | 规则+证据+LLM | 是 |
| Teaching Policy | LLM 可辅助 | 规则系统 | 是 |
| 教学解释 | 非常适合 | 通用 LLM | 可选 |
| 自然语言对话 | 非常适合 | 通用 LLM | 一般无需 |
| 个性化措辞 | 非常适合 | Prompt + Profile | 可选 |

因此，不应把“模型训练”简单理解成：

> 训练一个更懂斗地主的 GPT。

真正值得训练的是一些更加专门、更加可控的模型。

---

# 23A.3 通用 LLM 最适合承担的工作

当系统已经提供可靠结构化信息时，现代通用 LLM 很适合把这些信息转换成自然教学。

例如系统提供：

```json
{
  "playerRating": 57,
  "position": "farmer_down",
  "currentTrainingGoal": "farmer_cooperation",

  "playerMove": "2",
  "humanCoachMove": "pass",
  "oracleMove": "pass",

  "moveValues": {
    "pass": 0.74,
    "2": 0.31
  },

  "analysis": {
    "errorType": "farmer_cooperation",
    "severity": "high",
    "partnerHasInitiative": true,
    "controlCardWasted": true
  }
}
```

LLM 不需要自己重新计算牌局。

它的任务只是把结论转换成适合当前玩家水平的解释：

> 这里最重要的不是你的 2 能不能压住，而是没有必要抢队友的牌权。
>
> 队友已经取得主动，而且 2 是你以后限制地主的重要控制牌。
>
> 这一局只记住一个原则：
>
> **队友已经掌握主动时，先考虑他需不需要你帮助，而不是先考虑自己能不能压。**

这类任务正是通用 LLM 的优势。

---

# 23A.4 同一个结论可以根据玩家水平生成不同解释

例如同一个局面：

## 对 35 分玩家

只需要：

> 不要轻易压队友。
>
> 农民是两个人一起对付地主，队友已经拿到牌权时，一般应该先让他继续走。

---

## 对 60 分玩家

可以增加：

> 你的 2 不只是这一轮能不能赢的问题，它还是后续非常重要的控制牌。
>
> 如果没有必要，不应该提前消耗。

---

## 对 85 分玩家

才进一步分析：

> 这里 Pass 的优势来自下一次牌权交换，而不是当前这一墩。
>
> 地主的剩余长度以及已经出现的大牌，使保留 2 的残局控制价值高于立即抢权。

因此：

> **不同水平不需要不同 LLM。**

只需要给通用 LLM：

- Player Rating；
- 当前训练目标；
- 教学深度；
- 可使用的概念范围；

即可实现明显不同的教学体验。

---

# 23A.5 不应该让 LLM 自己判断“为什么玩家错了”

这是整个系统非常重要的可靠性边界。

错误做法：

```text
玩家刚才出了2。
请分析他为什么这么做。
```

LLM 可能生成一个听起来非常合理但实际上完全错误的原因。

例如真正原因可能是：

- 忘记 A 已经出了三张；

但 LLM 却判断成：

- 农民合作意识不好。

因此 Error Attribution 必须尽量建立在真实证据上。

例如系统提前计算：

```text
PartnerHasInitiative = true
PlayerStrongestControl = 2
PlayerBelievedRemainingA = 3
ActualRemainingA = 1
```

然后得到：

```text
MemoryError = HIGH
FarmerCooperationError = MEDIUM
ControlManagementError = LOW
```

再把这些证据交给 LLM。

这样 LLM 可以解释：

> 你的抢牌思路本身并不是完全错误。
>
> 真正影响这一步判断的是你认为外面还有很多 A，但此前实际上已经出现了三张。
>
> 所以这次主要属于记牌问题，而不是合作意识问题。

原则：

> **LLM 可以解释诊断，但不要让 LLM凭空创造诊断。**

---

# 23A.6 Player Rating 不应直接由 LLM 产生

不推荐：

```text
给你10局牌局记录，请把玩家水平打成1～100分。
```

原因包括：

- 模型输出存在随机性；
- Prompt 微调可能改变评分；
- 不同模型之间评分不可比；
- 模型升级可能使历史数据失去一致性；
- 很难解释“为什么是68而不是72”。

因此 Player Rating 应由稳定的算法计算。

例如记录：

```text
CriticalDecisionLoss
RepeatedMistakes
FarmerCooperationAccuracy
ControlCardMistakes
MemoryAccuracy
EndgameDecisionQuality
```

再计算：

```text
Farmer Cooperation = 61
Card Memory = 43
Endgame = 82
Overall = 67
```

LLM 只解释：

> 你目前大约是中等偏上水平。
>
> 残局处理明显强于平均，但记牌和农民配合正在限制进一步提升。

原则：

> **分数由算法产生。**
>
> **意义由 LLM 解释。**

---

# 23A.7 Human Memory V1 不需要神经网络

第一代 Human Memory Model 建议完全采用：

**Deterministic / Rule-Based Model**

例如：

```text
Memory Level 1

Jokers    100%
2          95%
A          80%
K          40%
Q/J        20%
Others     10%

Recent Move Bonus       +30%
Bomb Bonus              +100%
Landlord Key Move Bonus +20%
Time Decay              -x%
```

这样有几个优势：

- 容易调试；
- 容易解释；
- 容易调整不同难度；
- 容易做 A/B Test；
- 能明确知道 AI 当前拥有哪部分信息。

不要第一版就让 LLM：

> “假装你是一个普通高手，忘掉一些牌。”

这种方式：

- 不稳定；
- 不可重复；
- 不可 Benchmark；
- 很难判断问题来自哪里。

---

# 23A.8 最可能首先需要训练的是 Human-Limited Decision Model

现有 DouZero 类模型通常接受比较完整的历史和牌局特征。

它学到的是：

```text
完整历史
    ↓
准确状态特征
    ↓
最佳动作
```

但 Human Coach 真正需要的是：

```text
不完整的人类记忆
    ↓
带不确定性的 Belief State
    ↓
人类可执行的最佳动作
```

如果简单把 DouZero 的某些输入 feature 遮掉，模型可能表现异常。

原因是：

> 模型从来没有在这种不完整输入分布下训练。

因此未来很可能需要：

**Human-Limited Student Model**

例如：

```text
Oracle DouZero
     │
     │ Teacher
     ▼
Human Memory Filter
     │
     ▼
Limited Observation
     │
     ▼
Student Model
```

Teacher 拥有完整信息。

Student 只能使用：

- 有限记牌；
- 模糊牌数；
- 部分历史；
- 人类合理推断。

目标不是让 Student 超过 Oracle，而是：

> 在人类实际可获得的信息范围内，尽可能稳定地做出高质量决策。

这可能成为整个项目最有研究价值的专用模型。

---

# 23A.9 不建议训练“斗地主 LLM”

至少在前几个产品阶段，不建议投入资源训练一个：

> 专门懂斗地主语言的大模型。

原因：

底层最优动作已经由专用游戏 AI 负责。

通用 LLM 只需要理解类似：

```text
Player Rating = 63
Player action = 2
Recommended action = Pass
Error = Farmer Cooperation
Severity = High
Training Goal = Cooperation
```

这样的结构化数据。

这远远低于训练一个完整领域模型所需的难度。

而且通用 LLM 会持续进步。

未来更换：

```text
Model A
→ Model B
→ Model C
```

即可自动获得：

- 更好的表达；
- 更自然的语音；
- 更好的上下文理解；
- 更强的个性化能力。

因此语言模型应该尽量保持：

> **可替换组件**

而不是产品最深层的技术绑定。

---

# 23A.10 LLM 教练推荐演进路线

## V1 — Prompt Engineering

直接使用高质量通用 LLM。

提供：

```text
PlayerProfile
CurrentTrainingGoal
DecisionAnalysis
HumanCoachResult
OracleResult
GameContext
```

通过 System Prompt 控制：

- 角色；
- 教学方式；
- 解释深度；
- 是否纠正；
- 每次讲几个重点；
- 避免使用超出玩家水平的概念。

预计已经可以实现大部分核心体验。

---

## V2 — Few-Shot / Teaching Example Library

随着项目发展，积累典型教学案例。

例如：

```text
抢队友牌权
过早使用2
错误拆对子
错误保炸弹
没有送队友
地主错误控牌
记错A
残局顺序错误
```

每种问题准备少量高质量案例。

根据当前 Error Type 动态选择 2～5 个例子加入 Prompt。

这样可以：

- 提高解释一致性；
- 统一教学思想；
- 减少 LLM 自由发挥；
- 建立产品自己的“教学风格”。

仍然无需训练模型。

---

## V3 — Fine-Tuning

只有当积累足够真实教学数据以后才考虑。

训练数据应该是：

```text
玩家水平
+
局面
+
错误分类
+
玩家真实原因
+
教练解释
+
玩家反馈
+
后续是否改正
```

Fine-Tuning 的目标不应该是：

> 教 LLM 怎样斗地主。

而应该是：

> **教 LLM 怎样教斗地主。**

---

# 23A.11 最重要的训练数据：教学是否有效

普通 AI 项目容易收集：

```text
State → Best Move
```

但这种数据并不稀缺。

DouZero 可以自动产生大量数据。

真正稀缺的是：

```text
Player Profile
        ↓
Specific Weakness
        ↓
Teaching Intervention
        ↓
Future Behaviour
```

例如：

```text
Player Rating = 54

Weakness:
Farmer Cooperation

Before Coaching:
Error Rate = 41%

Teaching:
“队友取得牌权时不要急着抢回。”

Next 20 applicable situations:

Error Rate = 17%
```

这样的数据可以回答：

> **这个教学方法真的让玩家进步了吗？**

这会成为整个产品未来最有价值的数据之一。

---

# 23A.12 Teaching Effectiveness Model

长期可以建立一个模型，学习：

> 对哪一种玩家，哪一种解释方式最有效。

不同玩家可能适合不同教学方式。

例如：

### 玩家 A

喜欢简单规则：

> 队友有牌权，不要抢。

效果最好。

### 玩家 B

需要理解原因：

> 因为两个农民实际上共享牌权资源，抢队友会浪费双方控制牌。

效果最好。

### 玩家 C

喜欢具体牌例：

> 如果你这里不用 2，下一轮地主出 A 时你仍然可以控制。

效果最好。

最终 Teaching Policy 可以决定：

```text
Player X
+
Error Type Y
+
Skill Level Z
        ↓
Best Teaching Style
```

这是比单纯语言 Fine-Tuning 更重要的长期方向。

---

# 23A.13 最终模型架构

长期系统可能拥有三个不同层次的模型。

## Model 1 — Game AI

职责：

> 怎么打最好？

例如：

```text
DouZero
DouRN
AlphaDou
Custom RL Model
```

---

## Model 2 — Human / Player Model

职责：

> 一个这个水平的人通常能够知道什么？

以及：

> 这个玩家为什么会作出这个决定？

包括：

```text
Human Memory
Human-Limited Decision
Player Skill Model
Error Attribution
Teaching Policy
```

这是项目最值得长期投入的专用模型层。

---

## Model 3 — General LLM

职责：

> 怎么把这些分析讲给这个玩家听？

包括：

- 对话；
- 教学；
- 鼓励；
- 总结；
- 个性化措辞；
- 语音交互。

第三层应该尽量保持可替换。

---

# 23A.14 产品技术壁垒的重新定义

早期很容易把产品理解为：

```text
DouZero + GPT
```

但更准确的结构应该是：

```text
Game AI
    │
    ▼
Decision Analyzer
    │
    ├──── Oracle Analysis
    │
    └──── Human-Limited Analysis
                 │
                 ▼
            Player Model
                 │
                 ▼
          Error Attribution
                 │
                 ▼
          Teaching Policy
                 │
                 ▼
            General LLM
                 │
                 ▼
              AI Coach
```

其中：

### 容易替换

- DouZero；
- LLM；
- TTS；
- STT。

### 难以替换

- Player Model；
- Human Memory Model；
- Human-Limited Decision；
- Error Attribution；
- Teaching Policy；
- 玩家长期成长数据；
- 教学效果数据。

因此长期竞争壁垒应该重点建设在：

> **“理解玩家”**

而不仅仅是：

> **“理解斗地主”。**

---

# 23A.15 推荐模型开发优先级

在底层斗地主算法稳定以后：

## Priority 1

**Decision Logging**

必须从第一天开始积累。

---

## Priority 2

**Deterministic Player Rating**

建立可靠、可解释、跨版本稳定的评分体系。

---

## Priority 3

**Human Memory V1**

基于规则实现。

---

## Priority 4

**Error Attribution V1**

尽量依赖证据而不是 LLM 猜测。

---

## Priority 5

**Teaching Policy V1**

决定：

- 是否提示；
- 什么时候提示；
- 提示什么；
- 讲多深。

---

## Priority 6

**General LLM Integration**

接入通用模型完成自然教学。

---

## Priority 7

**Human-Limited Student Model**

当验证出简单 Memory Filter 无法稳定配合现有游戏模型时，再进行专门训练。

---

## Priority 8

**Learning-to-Teach**

拥有足够真实用户数据以后，训练 Teaching Policy / Player Model。

---

# 23A.16 V1 阶段明确不做的事情

第一版不建议：

- 训练自己的大语言模型；
- Fine-tune 一个“斗地主 GPT”；
- 用 LLM 决定最佳出牌；
- 用 LLM 直接维护牌局状态；
- 用 LLM 随机模拟人类遗忘；
- 让 LLM 自己决定玩家 1～100 分；
- 让 LLM 无证据判断玩家犯错原因。

这些功能看似容易，但会使系统：

- 不稳定；
- 不可验证；
- 难以 Benchmark；
- 难以积累长期一致的数据。

---

# 23A.17 什么时候才应该考虑训练模型

不要提前决定必须训练。

应该先实现 V1，再通过真实测试寻找瓶颈。

只有出现下面情况时才进入训练阶段：

### Human Memory 瓶颈

规则模型无法真实模拟玩家信息范围。

→ 训练 Memory / Belief Model。

### Human-Limited AI 瓶颈

现有 DouZero 在遮蔽信息后表现明显异常。

→ 训练 Student Model。

### Player Rating 瓶颈

规则评分无法预测真实水平。

→ 训练 Player Skill Model。

### Error Attribution 瓶颈

规则无法可靠判断错误来源。

→ 训练 Classification Model。

### Teaching Policy 瓶颈

不同教学策略效果差异明显。

→ 训练 Learning-to-Teach Model。

### LLM 表达瓶颈

已经有非常清晰的结构化分析，但通用 LLM 仍无法稳定形成所需教学风格。

→ 最后才考虑 Fine-Tuning LLM。

---

# 23A.18 最终原则

整个项目应该遵循：

> **能用确定性程序解决的问题，不交给 LLM。**

> **能用通用模型解决的问题，不急于训练专用模型。**

> **只有真实数据证明某个模块成为瓶颈以后，才针对那个模块训练。**

这样可以最大限度降低：

- 开发成本；
- GPU 训练成本；
- 模型维护成本；
- 技术复杂度；

同时仍然能够逐渐形成很深的产品技术壁垒。

第一阶段真正需要证明的不是：

> 我们有没有自己的大模型。

而是：

> **我们能不能准确理解一个玩家，并持续让他的斗地主水平提高。**

如果这一点成立，后续再训练任何模型都会有明确目标和高质量数据基础。
