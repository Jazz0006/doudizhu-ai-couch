# AI 斗地主实时语音教练：MVP 开发设计文档

**文档版本：** v0.1
**日期：** 2026-08-01
**项目阶段：** MVP / 第一版原型
**主要平台：** 手机网页（Responsive Web / PWA-ready）
**后续平台：** Android（优先）、iOS
**建议技术栈：** React + TypeScript + Node.js + WebRTC/WebSocket

---

## 1. 项目概述

### 1.1 产品定位

本项目是一款以“实时语音 AI 私人教练”为核心的单机斗地主教学应用。

用户在应用内与两名传统电脑玩家进行斗地主对局。应用自动掌握完整牌局状态，并将用户可见的牌局信息同步给 AI 语音教练。用户可以自然地询问：

- “我现在应该怎么出？”
- “为什么不建议出对 8？”
- “我这样出可以吗？”
- “地主可能还有什么大牌？”
- “刚才队友为什么不接牌？”
- “这一局我的整体策略是什么？”

AI 教练应像一个温暖、有性格、懂斗地主的老师或好友，能够自然讨论局面、解释策略、指出风险，并根据用户水平调整教学深度。

### 1.2 核心价值

本产品不是普通的“出牌提示器”，而是：

> 一个真正懂当前牌局、能与用户实时讨论、解释牌理，并陪伴用户逐渐进步的私人斗地主老师。

### 1.3 第一版核心组合

- 单机斗地主牌桌；
- 两名传统算法控制的电脑玩家；
- 低、中、高三个对手难度；
- 实时语音 AI 教练；
- 自动向 AI 提供结构化牌局状态；
- 用户可询问建议并讨论原因；
- 牌局结束后进行简短复盘。

## 2. MVP 目标

### 2.1 第一阶段要验证的问题

MVP 不追求完整商业化，而是验证以下核心假设：

1. 用户是否愿意在斗地主过程中频繁与 AI 教练对话；
2. AI 是否能够基于准确牌局状态给出有帮助的建议；
3. 实时语音交互是否足够自然；
4. 用户是否更喜欢“直接答案”还是“引导式教学”；
5. 用户每局平均使用多少语音时间；
6. 不同教练风格是否影响留存；
7. 低、中、高三档电脑玩家是否能形成合理学习梯度；
8. 用户是否愿意在对局结束后查看 AI 复盘。

### 2.2 MVP 成功标准

建议以小规模测试用户衡量：

- 80% 以上测试用户可以独立完成完整对局；
- AI 能正确读取和描述当前手牌、角色、出牌历史和剩余牌数；
- AI 不建议非法出牌；
- AI 不泄露其他玩家隐藏手牌；
- 语音响应能够被用户自然打断；
- 至少 60% 测试用户认为“比普通提示功能更有趣或更有帮助”；
- 平均每局产生不少于 3 次有效语音互动；
- 对局中断后可恢复当前牌局；
- 中等难度下，普通玩家不会感到对手明显愚蠢或作弊。

## 4. 产品体验原则

### 4.1 AI 是老师，不是自动代打

AI 不应默认替用户做所有决定。

优先交互方式：

1. 用户先选择牌；
2. 用户询问“这样出可以吗？”
3. AI 分析用户思路；
4. AI 给出风险、替代方案和理由；
5. 用户自己决定最终出牌。

可以提供“直接推荐”，但不能让用户长期只按推荐按钮。

### 4.2 AI 可以承认没有唯一答案

斗地主存在大量不完全信息。AI 必须区分：

- 确定事实；
- 合理推测；
- 风险判断；
- 教学简化；
- 接近等价的多个方案。

推荐表达：

- “这两种出法都成立。”
- “我稍微更偏向……”
- “按目前公开信息，还不能确定……”
- “这不是明显错误，但会留下一个风险。”
- “从结果看不好，不代表当时决策一定错。”

禁止表达：

- 将未知信息说成确定事实；
- 用虚构理由解释策略模型结果；
- 因知道隐藏牌而提供作弊建议；
- 将每一步描述为唯一正确解。

### 4.3 默认少说，用户需要时再展开

AI 不应每一步都长篇讲解。

建议三种交互层级：

- 简短提醒：一句话；
- 普通解释：2–4 句话；
- 深入分析：用户明确要求后展开。

示例：

用户：“我出对 8 可以吗？”

简短回答：

> 可以，但我更偏向先用三张 7 带一张小牌，因为你现在最难处理的是单牌。

用户：“为什么？”

再展开：

> 出对 8 会保留三个 7，但你的 3、9、10 仍然分散。三带一可以减少一张小单牌，同时保留对 8 作为后续衔接。两种都不是明显错误，我只是更喜欢后者的手牌结构。



## 8. 斗地主规则引擎

## 8.1 规则引擎职责

- 创建完整 54 张牌；
- 洗牌；
- 发牌；
- 分配三张底牌；
- 叫地主；
- 识别牌型；
- 判断牌型是否合法；
- 判断能否压过当前牌；
- 生成所有合法动作；
- 处理过牌；
- 判断一轮结束；
- 更新出牌权；
- 判断胜负；
- 记录历史；
- 状态序列化；
- 状态恢复。

## 8.2 推荐开发顺序

1. 单张、对子、三张；
2. 三带一、三带二；
3. 顺子；
4. 连对；
5. 炸弹、王炸；
6. 飞机；
7. 飞机带牌；
8. 四带二；
9. 所有合法动作生成；
10. 完整回合；
11. 叫地主；
12. 胜负判断；
13. 序列化与恢复。

## 8.3 规则测试要求

每一种牌型都必须包含：

- 正常合法案例；
- 边界案例；
- 非法案例；
- 与上一手比较案例；
- 炸弹覆盖案例；
- 王炸覆盖案例；
- 重复牌与长度错误案例。

特别注意：

- 顺子不允许包含 2 和王；
- 连对不允许包含 2 和王；
- 飞机连续三张不允许包含 2；
- 四带二的实现需明确采用哪个规则版本；
- 三带一与飞机带牌不能错误重叠；
- 过两家后重新获得自由出牌权。

## 9. 电脑玩家设计

## 9.1 基本原则

第一版电脑玩家采用传统确定性算法和有限搜索，不调用大语言模型。

电脑玩家目标：

- 合法；
- 快速；
- 可控；
- 难度稳定；
- 错误像人；
- 不作弊或明确区分是否允许读取全局状态。

建议默认电脑玩家只能访问：

- 自己的手牌；
- 公共底牌；
- 已出牌记录；
- 其他玩家剩余牌数；
- 当前牌面。

不要直接读取其他玩家手牌。

## 9.2 通用决策流程

```text
1. 生成所有合法动作
2. 为每个动作计算特征
3. 根据难度使用不同权重评分
4. 必要时进行有限深度搜索
5. 加入受控随机性
6. 返回动作
```

## 9.3 动作特征

每个候选动作至少计算：

- 出掉牌数；
- 出牌后估计剩余手数；
- 剩余单牌数量；
- 是否拆对子；
- 是否拆三张；
- 是否拆顺子；
- 是否拆炸弹；
- 是否消耗王或 2；
- 是否获得牌权；
- 是否阻止对手可能走完；
- 是否帮助农民队友；
- 是否给地主轻易接牌；
- 当前是否残局；
- 对手剩余牌数；
- 用户或队友是否只剩 1–2 张。

## 9.4 低难度

低难度模拟新手，而不是随机乱出。

特点：

- 主要考虑当前一手；
- 偏好一次出更多牌；
- 记牌能力弱；
- 经常过早使用大牌；
- 农民配合较差；
- 偶尔拆合理牌型；
- 仅进行浅层评估；
- 可能错误抢队友牌权；
- 叫地主主要看王、2、炸弹。

受控错误示例：

- 有 15%–25% 概率选择评分第二或第三动作；
- 忽略部分长期牌型结构；
- 在不危险时过早使用 A、2；
- 不进行未知牌推断。

## 9.5 中等难度

默认难度，模拟普通休闲玩家。

特点：

- 综合手牌结构；
- 尽量减少单牌；
- 基础记牌；
- 保留控制牌；
- 基础农民配合；
- 根据剩余牌数调整策略；
- 对残局进行 1–2 层搜索；
- 叫地主综合牌力与牌型；
- 偶尔存在合理失误。

## 9.6 高难度

特点：

- 更完整的手牌结构评分；
- 关键牌记忆；
- 未知牌概率估计；
- 农民协作；
- 残局搜索；
- 炸弹使用时机判断；
- 结合对手剩余牌数；
- 结合历史行为推断；
- 更低随机性；
- 更复杂叫地主评分。

高难度仍然不要求达到专业竞技水平，只需要明显优于中等难度。

## 9.7 可重复测试

电脑决策函数应支持随机种子：

```ts
chooseBotAction({
  state,
  seat,
  difficulty,
  randomSeed
});
```

这样可以：

- 重现错误；
- 比较算法版本；
- 回归测试；
- 给 Codex 自动测试稳定输入。

## 10. AI 教练系统

## 10.1 教练职责

AI 教练负责：

- 自然语言交流；
- 理解用户问题；
- 读取用户可见状态；
- 分析当前局面；
- 解释候选方案；
- 讨论用户选择；
- 根据用户水平调整表达；
- 提供鼓励；
- 在必要时调用牌桌工具；
- 复盘关键决策。

AI 教练不负责：

- 牌型合法性最终判断；
- 发牌；
- 回合控制；
- 电脑玩家动作；
- 胜负判断；
- 保存唯一牌局状态；
- 获取其他玩家隐藏牌。

## 10.2 AI 状态同步

不要在每次对话中发送完整自然语言描述。

应发送紧凑结构化状态：

```json
{
  "event": "game_state_update",
  "gameId": "abc123",
  "userRole": "farmer",
  "landlord": "left",
  "bottomCards": ["6", "9", "A"],
  "userHand": [
    "3", "4", "4", "7", "7", "7",
    "8", "8", "9", "10", "J", "J",
    "Q", "Q", "K", "A", "2"
  ],
  "currentTurn": "user",
  "currentWinningPlay": {
    "seat": "right",
    "type": "single",
    "cards": ["K"]
  },
  "remainingCardCounts": {
    "user": 17,
    "left": 19,
    "right": 16
  },
  "recentHistory": [
    {"seat": "left", "cards": ["3"]},
    {"seat": "right", "cards": ["K"]}
  ],
  "selectedCards": ["8", "8"],
  "selectedPlayLegal": true
}
```

### 10.3 不要每次重发全部历史

实现：

- 会话开始发送牌局初始状态；
- 每次状态变化发送增量事件；
- 定期发送状态快照纠正上下文；
- AI 需要完整历史时，通过工具查询；
- 对局过长时压缩旧历史。

建议事件类型：

```ts
type CoachGameEvent =
  | { type: "game_started"; state: PlayerVisibleGameState }
  | { type: "bid_made"; seat: Seat; bid: number | "pass" }
  | { type: "landlord_selected"; seat: Seat; bottomCards: Card[] }
  | { type: "cards_played"; seat: Seat; play: Play }
  | { type: "player_passed"; seat: Seat }
  | { type: "selection_changed"; cards: Card[] }
  | { type: "turn_changed"; seat: Seat }
  | { type: "game_finished"; winner: "landlord" | "farmers" };
```

## 11. AI 工具调用

建议给实时模型提供以下工具。

## 11.1 获取最新可见状态

```ts
get_current_visible_state(): PlayerVisibleGameState
```

用途：

- 用户询问“现在是什么情况？”
- 模型怀疑上下文过期；
- 发生语音中断后恢复。

## 11.2 分析用户选牌

```ts
analyze_selected_cards(): {
  selectedCards: Card[];
  legal: boolean;
  play: Play | null;
  warnings: string[];
}
```

## 11.3 获取合法动作

```ts
get_legal_actions(limit?: number): PublicLegalAction[]
```

只在 AI 需要候选出牌时调用。

## 11.4 高亮牌

```ts
highlight_cards(cardIds: string[], reason?: string): void
```

AI 可以说：

> “我说的是这三个 7，再带最小的 3。”

同时高亮对应牌。

## 11.5 清除高亮

```ts
clear_highlights(): void
```

## 11.6 请求局面辅助分析

```ts
evaluate_candidate_actions(
  actionIds?: string[]
): CandidateEvaluation[]
```

返回程序可计算特征，不要求第一版提供精确胜率。

```ts
interface CandidateEvaluation {
  action: PublicLegalAction;
  features: {
    remainingMoveEstimate: number;
    remainingSingles: number;
    breaksPair: boolean;
    breaksTriple: boolean;
    breaksBomb: boolean;
    usesControlCard: boolean;
    takesInitiative: boolean;
  };
  heuristicScore: number;
}
```

## 11.7 获取复盘数据

仅对局结束后可用：

```ts
get_post_game_review_data(): {
  fullHistory: PlayRecord[];
  fullInitialHands: Record<Seat, Card[]>;
  keyDecisionCandidates: DecisionPoint[];
}
```

## 12. AI 教练提示词要求

## 12.1 默认人格

- 温暖；
- 自然；
- 像熟悉用户的朋友或老师；
- 可以轻微幽默；
- 不过度撒娇；
- 不幼稚；
- 不过度奉承；
- 有主见；
- 用户方案不好时应明确指出；
- 语言简洁；
- 用户追问时再深入。

## 12.2 核心行为规则

系统提示应明确：

1. 只能基于用户可见信息分析实时牌局；
2. 不得推测自己看到了隐藏手牌；
3. 所有出牌合法性以工具结果为准；
4. 不得建议工具判定非法的动作；
5. 无法确定时必须说明不确定；
6. 多个方案接近时不要假装存在唯一答案；
7. 首先回应用户的想法，再给建议；
8. 解释应使用普通玩家能理解的牌理；
9. 少用抽象概率和模型术语；
10. 默认回答 1–4 句话；
11. 用户要求深入分析后再展开；
12. 允许主动问用户：“你自己更倾向怎么出？”
13. 不应每一步都主动说话；
14. 不应打断用户正常操作；
15. 对局结束后才允许参考完整隐藏牌。

## 12.3 默认回答结构

```text
1. 先评价用户方案
2. 给出推荐或风险
3. 给出一条核心理由
4. 必要时提供第二方案
```

示例：

> 出对 8 可以，而且不会破坏其他牌型。不过我稍微更偏向三张 7 带 3，因为你的小单牌比较难处理。两种都成立，主要看你想先整理手牌，还是保留三带一。

## 12.4 禁止行为

- “你必须这样出。”
- “地主肯定没有王。”
- “这是唯一正确答案。”
- 编造用户没有说过的出牌历史；
- 将电脑隐藏牌用于实时建议；
- 长篇重复全部手牌；
- 每轮自动总结；
- 说出与当前状态不一致的牌数；
- 直接替用户点击出牌，除非未来明确增加该功能。

## 13. 教练交互模式

MVP 可先实现一个默认模式，但架构预留以下枚举：

```ts
export type CoachMode =
  | "companion"
  | "coach"
  | "exam"
  | "beginner";
```

### Companion

- 自然聊天；
- 偶尔主动点评；
- 可以开玩笑；
- 更强调陪伴。

### Coach

- 仅在用户询问或明显错误时提示；
- 默认推荐模式。

### Exam

- 出牌过程中不提供答案；
- 可以问用户思路；
- 结束后复盘。

### Beginner

- 更频繁提示；
- 解释规则；
- 主动提醒明显风险。

MVP 默认使用 `coach`。

## 14.1 主牌桌页面

页面区域：

8. AI 高亮提示层；
9. 简短字幕显示。

## 14.2 语音按钮

MVP 建议优先：

- 点击开始对话；

  - 正在听；

- AI 新建议会替换旧高亮；

## 15. 状态管理

建议使用明确的有限状态机，避免 UI 和规则混乱。

```ts
type GamePhase =
  | "idle"
  | "dealing"
  | "bidding"
  | "landlord_reveal"
  | "playing"
  | "finished";
```

每个阶段明确允许的操作。

例如：

### `bidding`

- 用户可以叫分或不叫；
- 电脑可以叫分；
- 不允许出牌；
- AI 可以解释叫地主。

### `playing`

- 当前用户回合才允许选择和出牌；
- 非用户回合可查看牌；
- AI 可继续聊天；
- 电脑行动期间不阻塞语音。

### `finished`

- 禁止继续出牌；
- 显示结果；
- 允许完整复盘；
- 可以重新开始。

## 20. 成本控制

主要成本来自实时语音，不是电脑对手。

### 20.1 第一版成本策略

- 牌局完全本地运行；
- AI 沉默时不持续发送无意义音频；
- 状态使用增量更新；
- 不重复发送完整历史；
- 默认回答简短；
- 普通分析使用较低成本实时模型；
- 深入复盘可以切换文本模型；
- 每个匿名用户每日限制语音分钟数；
- 后端记录每局估算成本。

### 20.2 必须监控的指标

- 每局输入语音秒数；
- 每局输出语音秒数；
- 每局模型连接时长；
- 每局工具调用数；
- 每次回答平均延迟；
- 每局估算成本；
- 免费用户日均成本；
- 重度用户成本；
- 中断率；
- 重连成功率。

## 21. 对局复盘

- 使用炸弹；

- 拆炸弹；

- 对手剩余 1–2 张时的决策；
- 农民抢队友牌权；
- 用户跳过明显控制机会；
- 用户出牌后剩余手数明显增加；
- AI 曾明确讨论的动作；
- 最终胜负附近的动作。

## 22. 测试策略

## 22.1 单元测试

### 游戏规则

- 牌型识别；
- 牌型比较；
- 合法动作；
- 回合切换；
- 过牌逻辑；
- 胜负判断；
- 叫地主；
- 序列化。

### 电脑玩家

- 永不出非法牌；
- 永不出不存在的牌；
- 正确过牌；
- 不读取禁止信息；
- 固定种子结果稳定；
- 三档难度行为存在区别。

### 教练协议

- 可见状态不包含隐藏手牌；
- 状态事件正确；
- 工具输出可序列化；
- 高亮牌必须属于用户手牌；
- 复盘工具只在结束后可用。

## 22.2 属性测试

建议加入随机牌局自动运行：

- 批量生成 10,000 局；
- 所有牌始终唯一；
- 总牌数保持一致；
- 不出现非法动作；
- 对局最终可以结束；
- 不出现死循环；
- 状态恢复后结果一致。

## 22.3 集成测试

- 用户出牌 → 状态更新 → AI 获得事件；
- AI 高亮 → UI 正确显示；
- 会话断开 → 重连 → AI 获取最新状态；
- 刷新网页 → 恢复对局；
- 游戏结束 → 完整复盘可用。

## 22.4 人工体验测试

重点观察：

- AI 是否太啰嗦；
- AI 是否经常复述牌面；
- AI 是否能理解“这样出”；
- AI 是否会忘记当前选牌；
- 用户打断是否自然；
- 对手难度是否合理；
- 教练是否泄露隐藏信息；
- 用户是否依赖推荐而不思考；
- AI 是否敢指出用户错误；
- AI 是否会编造理由。

## 26. Codex 实施原则

Codex 在实现时应遵循：

1. 优先建立可测试的 `game-core`，不要先写复杂 UI；
2. 每增加一种牌型同时添加测试；
3. 不在 React 组件中实现核心游戏规则；
4. 不让 AI 模型成为牌局状态的唯一来源；
5. 不将 API 密钥放进客户端；
6. 不让实时教练读取 `FullGameState`；
7. 所有电脑动作必须通过统一合法动作生成器；
8. 使用 TypeScript 严格模式；
9. 对外接口使用明确类型；
10. 复杂逻辑添加注释和设计说明；
11. 每个里程碑保持应用可运行；
12. 避免一次实现所有高级功能；
13. 先完成确定性规则，再接入 AI；
14. 增加随机测试防止边界错误；
15. 所有网络失败必须有用户可见状态；
16. 牌局在 AI 断线时仍可继续；
17. AI 高亮只提示，不自动出牌；
18. 复盘与实时教练严格使用不同权限；
19. 每次合并前运行完整测试；
20. README 中持续更新启动和部署步骤。

## 28. 第一阶段完成后的评估

MVP 发布后，应重点回答：

- 用户每局问了多少次；
- 用户最常问什么；
- 是地主还是农民更需要教学；
- 用户更喜欢直接建议还是反问引导；
- 教练说话是否过多；
- 哪种回答最容易让用户继续交流；
- 哪种错误最常见；
- 中等难度是否适合作为默认；
- 用户是否愿意再玩第二局；
- 用户是否愿意为更多语音时间付费；
- 实时语音每局实际成本是多少；
- 网页在 iPhone 上是否足够稳定；
- 是否需要尽早封装 Android App。

## 30. 最终产品定义

第一版最准确的定义是：

> **传统单机斗地主牌桌 + 两名可调难度电脑玩家 + 一名真正懂当前局面的实时语音 AI 私人教练。**

开发优先级必须始终围绕这一体验：

1. 牌局状态准确；
2. 对话自然；
3. 建议可靠；
4. 解释易懂；
5. 不泄露隐藏信息；
6. 不打断游戏；
7. 成本可控；
8. 用户愿意继续玩。
